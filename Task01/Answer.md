# Task 1

Inputs are vehicle registration, vehicle category, user role (student, staff or visitor), entry and exit date/time, pass details, a charging request and consumed kWh. Facility configuration supplies each floor capacity. Outputs are a unique ticket, allocated floor/slot, availability or rejection, exit fee and total collection.

The nouns identify these classes: Vehicle stores identity and supplies the hourly-rate behaviour; TwoWheeler and Car supply different rates; ElectricCar adds Chargeable behaviour; Slot owns one position and its occupancy; ParkingTicket links vehicle, slot, entry, role and pass; ParkingFacility controls allocation, duplicate detection and exit; Pass represents parking entitlement; MonthlyPass checks registration, role and month; PricingRule separates the billing policy from allocation. A separate Floor class is unnecessary because a row of Slot[][] already represents a floor. Roles are validated strings because their only original behavioural difference is pass eligibility. Verbs become enter(), exit(), occupy(), release(), calculateFee(), chargingFee() and covers(). Each class protects the information needed for its own responsibility.

A slot holds at most one vehicle. One registration has at most one active ticket within a facility. Registration is normalized to uppercase. New tickets have different identities across facilities; the process UUID plus shared counter prevents reuse in a run and makes cross-run collisions negligibly unlikely rather than mathematically impossible. Strict durable uniqueness would require persistent numbering. Entry must not follow exit; durations and kWh cannot be negative. A charging booking requires a Chargeable vehicle and a charging slot. Invalid exit requests leave the ticket and slot unchanged. Passes waive only parking, never electricity. Occupancy is derived per facility, rather than shared globally.

Assumptions: general slots accommodate all categories; the last slot on every floor with at least two slots is reserved for charging. A one-slot floor is general. Floors and slots use zero-based indexes. Rates are Rs 10/hour for two-wheelers and Rs 30/hour for cars/EVs; every started hour is billed and zero minutes costs zero. No daily cap is imposed because no cap value was specified. Valid monthly passes are registration-bound, restricted to staff/students and must cover both endpoints of the stay. All times are local campus times. The application is single-threaded and in-memory.

Alternative: parallel arrays String[] regNo, String[] type and LocalDateTime[] entryTime store matching records at the same index. Search uses FOR i FROM 0 TO n-1; IF regNo[i] = key THEN RETURN i; ENDIF; ENDFOR. Searching an object array and the parallel arrays both take O(n L) worst-case, where L is registration length; for bounded registrations this is O(n). Both need O(1) search workspace. Each vehicle uses O(1) fields/references plus O(L) registration storage in either representation; total O(n) for bounded strings. Objects add header/alignment overhead, while parallel arrays add three array headers and require index synchronization. Adding a colour field requires one field and constructor change in Vehicle; parallel arrays require a fourth array, coordinated resizing and coordinated updates at every insertion/deletion site. Adding the field for n existing records takes O(n) total initialization in both designs; per-vehicle storage remains O(1).

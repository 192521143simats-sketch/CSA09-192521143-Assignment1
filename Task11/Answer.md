# Task 11

The integrated implementation is in src/parking. Task11/SystemTests.java executes normal operation, rounding boundaries, rejected operations, passes, equality and ticket identity. Every assertion prints expected and actual values, and any mismatch throws AssertionError. Tests use explicit timestamps rather than the wall clock. The full test table is the executed output following this answer; it contains actual results rather than unexecuted predictions.

Hand calculation: a two-wheeler, car and EV each park for 130 minutes. Three started hours give Rs 30 + Rs 90 + Rs 90; EV electricity adds 10*12 = Rs 120. Total = Rs 330. Tests assert each exit, total collection 330 and zero remaining occupancy. Exact-hour 60 minutes is Rs 30, 61 minutes is Rs 60, zero is Rs 0. A positive second or nanosecond still counts as a started hour. Normal, full-capacity, duplicate registration, invalid floor/slot, expired pass, visitor monthly misuse, unknown type and failed-exit atomicity cases are checked. The standalone Task03 execution additionally proves release/re-release and reallocation behaviour.

Encapsulation is supported by private arrays/fields and validated operations. Inheritance supplies shared registration/fee behaviour. Polymorphism chooses rates without client category chains; Chargeable is a capability. Abstraction separates Pass and PricingRule from the facility. A limitation is in-memory, single-threaded state: tickets and collection are not persisted and admission is not synchronized. Different independent facilities do not enforce campus-wide active-registration exclusivity. The UUID prefix is probabilistic across process restarts; strict permanent ticket uniqueness requires durable state. These are explicit limits rather than claims of production readiness.

Allocation and exit scan a fixed-capacity array. Let N be total capacity and n active vehicles: lookup and insertion are O(N) worst-case even when n is small, because empty entries remain. Full dense occupancy gives N=n. release of a known position is O(1). Array storage reserves O(N) references; retained tickets/vehicles use O(n). Slot storage is O(N+F).

Alternative exit with ArrayList: FOR ticket IN activeList; IF ticket.reg=key THEN calculate, release slot and remove ticket; ENDIF. Lookup is O(n), removal shifts O(n), total O(n); storage O(n) with spare capacity. HashMap<String,ParkingTicket>: t=active.get(normalizedReg); validate and calculate before mutation; release t.slot; active.remove(key). Lookup/removal average O(1) with bounded registration length and a healthy hash distribution, worst-case O(n) under general hashing assumptions (modern Java may treeify some collision bins). Hashing strings costs O(L) initially. HashMap uses O(n) space with buckets/nodes and higher constant overhead than array references. Replacing the map does not improve a separate O(N) slot scan.

Task11/LookupBenchmark.java measures last-element successful lookup at n=20,150,500, 10000 warm-up and 20000 timed repetitions per structure. Each lookup result reaches a volatile sink. All structures share the same prebuilt tickets, and setup is outside timing. It measures lookup alone, not fee computation/removal or memory bytes. Results vary with JIT, CPU and run order and do not establish formal Big-O. Exact retained bytes were not measured; the space comparison is structural. Actual CSV timings follow.

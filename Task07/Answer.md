# Task 7

TwoWheeler.ratePerHour() and Car.ratePerHour() override the abstract Vehicle method. Vehicle.calculateFee() calls that method, so the correct rate is selected even though the calculation is inherited. ElectricCar implements Chargeable.chargingFee() at Rs 12/kWh. Different rates and optional charging are the reasons for these specializations; duplicating all the fee arithmetic in every subclass would spread rounding rules.

@Override asks the compiler to check that a superclass/interface method is actually overridden. Name and parameter types must match; primitive return types must match, and reference returns may be covariant. Access cannot be narrowed; checked exceptions cannot be widened. A static method is hidden, not dynamically overridden; private methods are not inherited overrides. The completed exercise's chargingFee satisfies the interface even without an annotation; shared source uses @Override.

regNo is final to keep vehicle identity stable in sets/maps. equals() and hashCode() are final in the shared base so a subclass cannot break symmetry by adding category to equality. ParkingTicket is a final immutable class; its fixed fields cannot be reassigned. The final slots/active references prevent replacing the arrays, but their elements remain mutable. These uses of final protect specific invariants and do not make the entire application immutable.

Vehicle.toString() returns runtime class name and registration. equals() accepts any Vehicle with the same normalized registration. hashCode() uses exactly that registration. Therefore a Car and ElectricCar with TN02B2 compare equal and collapse to one HashSet entry. This is appropriate because identity is registration, not a mutable category classification; duplicate active admission is prohibited. A jurisdiction with identical plates from different regions would require a combined region-and-registration identity.

Alternative: calculateFee(minutes) switches on a type enum and returns hours * rate selected by case. For k types, a linear if/else chain may take O(k) comparisons. A Java switch over a dense enum/int can be O(1), while string-switch implementation/collision behaviour is not an unconditional O(1) guarantee. Both use O(1) temporary space. Virtual dispatch is normally O(1) with respect to k. Adding a rate in a switch changes the central fee class (and enum/factory as applicable); adding a subclass leaves Vehicle fee arithmetic unchanged but adds a class and updates the external creation registry. In the inherited-template design the common fee formula remains in one place.

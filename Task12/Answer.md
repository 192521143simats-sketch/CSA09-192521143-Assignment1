# Task 12

A. The changed requirements add flat-fee e-bikes, delivery vans with double car pricing only during 09:00-17:00, visitor one-day passes, and five unequal floors. Vehicle category, pricing, entitlement and facility configuration are affected; ticket identity, allocation, release and encapsulation rules remain the same. A rectangular index f*S+s assumes equal floor sizes. The existing jagged Slot[][] accepts five row lengths directly, so no allocation rewrite is needed.

B. The original hierarchy can add EBike and DeliveryVan subclasses without changing Vehicle, Car, TwoWheeler or ElectricCar. Simple hourly categories fit ratePerHour(); a time-dependent van rule does not fit a method receiving only minutes. The existing PricingRule interface already receives entry and exit times, so a new policy can specialize van pricing without moving time-window logic into ParkingFacility. Identity/rounding stay shared; the changed window rule is centralized in one new policy. Pass is already a capability contract, so OneDayPass is an additional implementation. The original Main factory remains a baseline app with its original three categories; a separate ChallengeDemo constructs the extended categories without altering its switch.

C. Decision: RETAIN the core model and MODIFY the application by extension and configuration. Add EBike extends Vehicle, DeliveryVan extends Car, ChallengePricing implements PricingRule, and OneDayPass implements Pass. Configure capacities {2,3,4,2,5}. Two existing classes are tightened: ParkingTicket.getSlot() now returns an immutable Position record, and ParkingFacility uses that position to release its privately held slot. This closes a mutable-reference leak while retaining admission and pricing behaviour. Existing model/service classes changed: 2. New shared classes: 4; new demo and tests are additional evidence. If one combined interactive category factory were required, its registry would need two entries; this separate deterministic entry point avoids changing the baseline factory.

Assumptions for underspecified prices: e-bike flat parking fee is Rs 20 for any positive stay, zero for zero duration. One-day pass is registration-bound, visitor-only, and covers one calendar date; both endpoints must lie on that date, so exit exactly at next midnight is not covered. Purchase price is not specified and is not included in collection. Monthly/day passes waive parking only. Delivery vans use Rs 30 per off-peak hour and Rs 60 per peak hour; parking is partitioned by each calendar day's 09:00 and 17:00 boundaries, charging proportional elapsed minutes in each band and rounding the final rupee total upward. This deliberately avoids independently rounding every band to a full hour or doubling an entire mixed stay. It is a changed rule specifically for vans; other categories retain started-hour billing. Tests use minute-aligned van timestamps; arbitrary seconds are priced proportionally too.

Window algorithm: cursor=entry; WHILE cursor<exit: select next boundary among 09:00,17:00,next midnight; end=min(boundary,exit); rate=60 if cursor in [09:00,17:00), otherwise 30; add elapsedSeconds*rate; cursor=end; ENDWHILE; return ceiling(total weighted seconds /3600), including subsecond remainder. This runs O(D) time over D calendar days and O(1) workspace. The standard fee remains O(1), while jagged allocation is O(N) and ticket lookup O(N). Flat e-bike billing and pass checks take O(1).

D. Evidence: existing changed classes are ParkingTicket and ParkingFacility (2); four new shared classes implement the additional categories, pass and pricing. Original SystemTests is rerun after extension, and ChallengeTests checks e-bikes, peak/off-peak vans, mixed-window and overnight intervals, zero/negative durations, day-pass validity/expiry, five unequal floors, full capacity and charging suitability. Hand checks: 08:00-10:00 van = 30+60=90; 16:30-17:30 = 30+15=45; 09:00-17:00 = 8*60=480; 17:00-09:00 next day = 16*30=480. A further plain hourly type needs one subclass and creation at the app boundary; a new time-based policy needs a new PricingRule and explicit policy selection. Trade-offs are the longer O(D) van calculation, more small policy classes and a deliberate documented rounding difference. These are preferable to rewriting the allocation algorithm or spreading time windows over all vehicle classes. The final recommendation follows the two small encapsulation changes, four extension classes and executed regression/new-category results.
